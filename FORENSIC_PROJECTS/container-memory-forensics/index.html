Container Memory Forensics

Advanced Docker & Kubernetes Runtime Analysis

Project Overview

Container Memory Forensics is an advanced tool for analyzing the memory of Docker and Kubernetes containers (lightweight, isolated environments that run applications) in production environments. The system detects anomalies, analyzes compromised containers, identifies malware, and enables post-breach investigation (examining a system after an attack) without stopping running services. It uses a modified version of the Volatility Framework (an open-source tool for analyzing computer memory/RAM dumps) adapted to work with namespaces (Linux kernel features that isolate processes so containers are separated from each other) and cgroups (control groups — a Linux feature that limits how many resources, such as CPU and memory, a container can use).

System Architecture

The system consists of an agent running on every node (a physical or virtual machine in the cluster) as a DaemonSet (a Kubernetes object that ensures a pod runs on every node in the cluster). It uses eBPF (Extended Berkeley Packet Filter — a Linux kernel technology that safely monitors system activity without modifying kernel code) to monitor syscalls (system calls — requests a program makes to the operating system), and a custom kernel module for safe memory acquisition. A central console aggregates the data and enables deep forensic analysis.

The memory acquisition process uses a combination of /proc/[pid]/mem (a special Linux file that exposes a process's memory) and a custom kernel module for regions not accessible from user space (the safe, restricted area where normal programs run, as opposed to kernel space where the OS core runs). The system preserves evidence integrity by generating SHA-256 hashes and maintaining a chain of custody (a documented record proving evidence was not tampered with).

Kubernetes Pod Forensics

A specialized module for analyzing Kubernetes pods (the smallest deployable unit in Kubernetes, which can contain one or more containers), including multi-container pods, init containers (containers that run setup tasks before the main container starts), and sidecar patterns (helper containers that run alongside the main container). The system can reconstruct ConfigMaps (Kubernetes objects storing non-sensitive configuration data) and Secrets (Kubernetes objects storing sensitive data like passwords) from memory even after they have been deleted from etcd (the key-value database that stores all Kubernetes cluster state).

Pod Analysis

Complete analysis of all containers in a pod, including shared volumes (storage shared between containers) and inter-container communication through shared memory.

Service Mesh

Dedicated support for Istio/Linkerd sidecars (service mesh tools that manage network traffic between microservices). Analyzes mTLS certificates (mutual TLS — where both sides verify each other's identity), routing rules, and policy violations from Envoy proxy (a high-performance network proxy used by service meshes) memory.

Secrets Recovery

Extraction of Kubernetes secrets (stored sensitive data such as API keys and passwords), service account tokens (credentials that allow pods to authenticate with the Kubernetes API), and sensitive environment variables from process memory.

eBPF Runtime Monitoring

syscall_monitor.c - eBPF Syscall Tracer

The eBPF (Extended Berkeley Packet Filter — a Linux kernel technology that safely monitors system activity without modifying kernel code) module monitors in real-time all syscalls (system calls — low-level requests a program makes to the OS kernel) made by containers. It detects suspicious patterns such as privilege escalation attempts (trying to gain higher-level permissions than allowed), kernel exploitation, and container escape (when malicious code inside a container breaks out and accesses the host system) techniques.

Memory Injection Detection

An advanced module that detects various memory injection techniques used by malware inside containers. Analysis covers process hollowing (replacing legitimate process code with malicious code in memory), reflective DLL injection (loading a malicious library entirely from memory without writing it to disk, used in Windows containers), and LD_PRELOAD hooking (forcing a process to load a malicious shared library that intercepts standard function calls).

Case Studies

Case 1: Kubernetes Cluster Cryptojacking

Detection and analysis of a large cryptojacking (hijacking computing resources to mine cryptocurrency without the owner's consent) campaign in a Kubernetes cluster. The attackers exploited misconfigured RBAC (Role-Based Access Control — a security method that gives users/processes only the permissions they need) to deploy a DaemonSet (a Kubernetes object that ensures a pod runs on every node) containing a cryptominer (malware that secretly mines cryptocurrency). Memory forensics allowed identification of the command & control infrastructure (servers the attacker uses to remotely direct the malware) even after the attackers had deleted all files from disk.

# Impact Analysis:
Affected nodes: 47/52
Mining duration: ~3 weeks
Estimated profit: 2.3 XMR (~$350)
Cloud costs: $12,000+

Case 2: Supply Chain Attack via Container Image

Analysis of a supply chain attack (an attack that compromises software before it reaches the end user, for example by tampering with a widely used base image) where a popular base image (the starting template used to build container images) had been compromised. Memory forensics detected a backdoor (hidden access mechanism planted by an attacker) that was activated only under specific conditions, making it undetectable by standard image scanners (tools that check container images for known vulnerabilities).

Integration & API

forensics_api.go - gRPC API Service

The system exposes REST (a standard web API style using HTTP requests) and gRPC (a high-performance remote procedure call framework developed by Google) APIs for integration with SIEM/SOAR platforms (Security Information and Event Management / Security Orchestration, Automation and Response — tools used by security teams to collect alerts and automate responses). It supports webhooks (HTTP callbacks triggered by events) for real-time alerts and a batch API for scheduled forensics scans. Native integrations with Elasticsearch, Splunk, and Prometheus are included.

Conclusions & Future Directions

Container Memory Forensics fills a critical security gap in cloud-native environments (systems built and run in the cloud using containers and microservices). This project gave me a deep understanding of Linux namespaces (kernel features that isolate processes), cgroups (control groups — resource-limiting features), container runtimes, and kernel-level programming. Combining memory forensics with container technology opens new possibilities in incident response (the process of identifying, containing, and recovering from a security breach) and threat hunting (proactively searching for hidden threats inside a network).

Planned extensions include support for Windows containers, integration with Falco (an open-source runtime security tool for cloud-native environments) for real-time response, and a module for automated remediation (automatically fixing or isolating detected threats) of discovered threats. I am also considering adding support for serverless platforms (Lambda, Cloud Functions — services that run code without managing servers).
